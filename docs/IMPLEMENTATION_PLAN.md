# Реализованная архитектура v3

Один Python-проект обслуживает сайт и API. HTML/CSS/JS не требуют сборки. `service.py` общий для стандартного HTTP-сервера и optional FastAPI: переключение HTTP-фреймворка не меняет модель или формат прогноза.

Поток: `data/raw/*.csv` → `data.load_hourly()` → `train.train_models()` → `artifacts/` → `weather.fetch_weather()` → `agent.run()` → `storage` → `service.dashboard_forecast()` → браузер. Фронт получает погодные признаки из сохранённого результата того же расчёта, без второго запроса погоды.

Чат использует этот же сервис. В local-режиме формирует ответы по правилам; при явной конфигурации OpenAI вызывает Responses API с ограниченным контекстом. Языковая модель не изменяет расчёт мощности и не обходит временные проверки.

`as_of_date` — локальная полночь; метки API — UTC. Полные часы SCADA доступны после завершения интервала. Инициализация погодного выпуска и условная доступность проверяются относительно origin. Документально подтверждённой публикации для поставленного hindcast-архива нет; строгий режим его отклоняет.

Детали запуска, измеренные метрики и оставшиеся ограничения находятся в актуальном README. Проверки — в `docs/SUPERVISOR_REVIEW.md`. Ранние формулировки о гарантированной утечке/точности не являются текущими свойствами системы.

## Текущий режим

Новый `LiveForecastAgent` использует свежую погоду и рабочие v2-артефакты. `service.live_dashboard()` приводит результат к общей схеме фронта. `mode=backtest` и `mode=live` проходят отдельные временные проверки; live-погода не используется как историческая. Оба режима сохраняют фактические признаки расчёта и журнал в SQLite.

Физические пороги из нового архива сохранены в отдельном отключённом сценарии. Неподтверждённая конфигурация 2,5 МВт не включает перевод единиц. Модельные ответы чата рассчитывают сравнительные статистики из одного результата и не запрашивают вторую, потенциально отличающуюся погоду.
