# Пакет для экспертного просмотра

## Назначение и основной сценарий

Wind Agent показывает полный путь от измерений двух турбин и погодных входов к прогнозу мощности: загрузка и проверка временного ряда, вычисление признаков, модель T1/T2, правила агента, сохранение происхождения расчёта, HTTP API и браузерная панель. Пользователь может выбрать исторический срез или запросить текущую погоду, сравнить 24- и 48-часовой горизонт, исследовать график, задать контекстный вопрос локальному аналитику и выгрузить таблицу.

Система рассчитана на локальную демонстрацию и проверяемый анализ. Она не должна представляться как точная система коммерческого планирования до проверки временных допущений, архивной доступности погоды, нормализации и февральских фактических значений.

## Структура и технологии

| Слой | Реализация | Проверяемые файлы |
|---|---|---|
| Наблюдения | CSV с десятиминутными рядами T1/T2; очистка, контроль дублей и полноты, агрегация полных часов | `data/raw/`, `windagent/data.py`, `reports/dataset_profile.json` |
| Обучение и инференс | scikit-learn HistGradientBoosting; отдельная модель на турбину; хеши артефактов и схемы признаков | `windagent/model.py`, `windagent/train.py`, `artifacts/metadata.json` |
| Погодные входы | ECMWF IFS через Open-Meteo, архивные выпуски и текущая загрузка, кэш, проверка временной доступности и сохранение provenance | `windagent/weather.py`, `windagent/live_weather.py`, `data/weather/`, `docs/WEATHER.md` |
| Политика агента | Валидация временного среза, получение входов, запуск модели, предупреждения, идемпотентный повтор и аудит в SQLite | `windagent/agent.py`, `windagent/live.py`, `windagent/storage.py` |
| Сервис и интерфейс | Python HTTP-сервер; FastAPI/Uvicorn как опция; HTML/CSS/JavaScript/SVG без npm | `windagent/service.py`, `windagent/server.py`, `windagent/api.py`, `index.html`, `app.js`, `styles.css` |
| Диалог | Локальные аналитические правила; опционально серверный OpenAI Responses API | `windagent/chat.py`, `.env.example` |

## Модель и числовое доказательство

Обучение ограничено срезом `2026-02-01T00:00:00+05:00`. Для выбора использовались три последовательных окна; январь 2026 отделён как финальная проверка. Час учитывается, только если доступны 6/6 десятиминутных измерений. После январской оценки выбранные кандидаты переобучены на всех допустимых до среза данных. Метаданные содержат временные границы, версии библиотек, SHA-256 исходных CSV и моделей, кандидатов и метрики.

На 744 январских часах каждой турбины conditional-power-v2 получила MAE 0.02187 (T1) и 0.02404 (T2); исходный HGB-кандидат на тех же часах — 0.02390 и 0.02536. Ошибка измерена в единицах нормализованной мощности **при фактической погоде**. Это доказательство качества регрессии мощности при известных погодных признаках, не точности погодного прогноза или целого 24/48-часового конвейера. Для T2 RMSE вырос с 0.06355 до 0.06413, что явно зафиксировано в отчёте.

Отдельная январская реконструкция использует семь origin и 672 сопоставленные строки. Сохранённые погодные значения имеют метку hindcast и `as_of_verified=false`; предполагаемый лаг публикации 12 часов не подтверждён доказательством фактической выдачи в тот момент. Февральская реконструкция содержит 28 срезов / 2 688 значений, но фактических февральских мощностей нет, поэтому точность для февраля не измерена.

## Единицы и рабочие допущения

- Пользователь проекта подтвердил номинал 2,5 МВт для каждой турбины.
- Источник не документирует, как рассчитана колонка «Нормализованная активная мощность». В конфигурации преобразование в MW/MWh обозначено как допущение, что нормализованное значение — доля номинала. Интерфейс и отчёты должны сохранять эту оговорку.
- `Asia/Almaty`, timestamp `start` и нулевая задержка телеметрии — явные, пока не подтверждённые предположения. Исторические неоднозначные отметки при смене UTC смещения исключаются.
- В конфигурации этой демонстрационной сборки включён исследовательский cut-in/rated/cut-out сценарий. Пороги не подкреплены паспортом турбины; сценарий меняет постобработку прогноза, а январские метрики conditional модели посчитаны до этой коррекции.
- Исторический режим — реконструкция по кэшу, live-режим — запрос актуального прогноза. Fixture-тесты live-маршрутов доказывают корректность обработки запроса, но не успешную загрузку из сети. Свежий network smoke-test нужно оценивать по его отдельному результату.

## Воспроизводимость

Из корня проекта установка и запуск выполняются командами `.\start.ps1` на Windows или `bash start.sh` на macOS/Linux. Виртуальное окружение и зависимости закреплены в `requirements.lock.txt`; модели включены в `artifacts/`. Версии обучения записаны в метаданных. Для контролируемого переобучения:

```sh
python -m windagent train --cutoff 2026-02-01T00:00:00+05:00 --timezone Asia/Almaty --timestamp-semantics start --min-samples 6 --validation-months 6 --folds 3
```

Команда изменит артефакты и отчёты обучения в этой копии. Для fresh-прогноза с внешним API:

```sh
python -m windagent live --horizon 48 --refresh --output reports/live_forecast.json --csv reports/live_forecast.csv
```

Закреплённый результат проверки ревизии находится в `reports/model_revision_audit.json`; независимые протоколы — в `reports/service_verification.json`, `reports/weather_provenance_audit.json`, `reports/live_verification.json`, `reports/live_http_verification.json` и `reports/supervisor_verification.json`. Проверки без внешней сети:

```sh
python -m unittest discover -s tests -v
python scripts/verify_weather.py
python scripts/verify_service.py --real
python scripts/verify_delivery.py
python scripts/verify_live.py
python scripts/verify_live_http.py
python scripts/verify_chat_tools.py
python scripts/verify_model_revision.py
```

При описании результатов отдельно называйте офлайн фикстуры, архивную реконструкцию и свежий API-запрос. Только последний подтверждает, что API успешно ответил в конкретном live-запуске; он всё равно не подтверждает точность будущего прогноза без будущих SCADA фактов.

## Рекомендованный порядок защиты

1. Покажите полный поток и источники: CSV → почасовые строки → метаданные модели → прогноз и API → панель и CSV.
2. Откройте `reports/training_report.md`; объясните разницу между conditional holdout и прогнозом по будущей погоде.
3. Покажите предупреждение provenance в историческом режиме и метку неподтверждённой доступности hindcast.
4. В live режиме выполните обновление погоды, покажите время/источник конкретного ответа и только затем называйте запуск сетевым успешным.
5. Укажите номинал 2,5 МВт как подтверждённый пользователем ввод, а формулу пересчёта нормализованного сигнала как предположение; не скрывайте это за форматированием интерфейса.

Карта требований и доказательств конкурса находится в [docs/CRITERIA.md](CRITERIA.md). Она описывает факты и ограничения; баллы выставляют проверяющие.
